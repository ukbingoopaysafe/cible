# تصميم إعادة تسمية ما بعد الصفقة إلى متابعة العميل

**الحالة:** معتمد من المالك — 2026-11-04
**آخر تحديث:** 2026-11-04

## الهدف

توحيد الاسم العربي والاسم الداخلي للمسار المستقل الذي يستمر فيه التواصل مع العميل بعد نجاح صفقة، ليصبح **متابعة العميل**. التغيير يخص المصطلح ومراجع الكود والواجهات والوثائق؛ لا يغيّر قواعد المسار أو بياناته أو جداول قاعدة البيانات.

## النية المعتمدة من المالك حتى الآن

- الاسم الجديد هو «متابعة العميل».
- تظل متابعة العميل مستقلة عن متابعة الطلب النشط.
- يبدأ المسار بعد أول صفقة ناجحة مرتبطة بعميل معروف. وإذا أُضيف العميل إلى طلب ناجح بعد الصفقة، يبدأ المسار عند ربطه.
- يبقى عمودا جدول العملاء، ويصبح اسماهما «مسؤول المتابعة» و«المتابعة القادمة».
- يشمل التغيير أسماء الكود والواجهات والوثائق، مع إبقاء أسماء جداول قاعدة البيانات وأعمدتها كما هي.

## السلوك الحالي الذي يجب أن يبقى

- لكل عميل في كل قسم سجل متابعة واحد مستمر؛ لا تدمج سجلات الإيجار وإعادة البيع.
- يبدأ السجل تلقائيًا عند إنشاء صفقة ناجحة مع عميل معروف، ويمكن بدء سجل عميل يدويًا فقط إذا كانت له صفقة ناجحة بالقسم نفسه.
- يمكن ربط التفاعل بصفقة تخص العميل والقسم نفسيهما. القناة والوقت والنتيجة مطلوبة، والملاحظات والإحالة وموعد المتابعة القادم اختيارية.
- يسجل كل تفاعل كتاريخ يدوي لا يقبل التعديل أو الحذف من الواجهة. يظل موعد متابعة العميل اختياريًا ومستقلًا عن موعد متابعة الطلب.
- يستمر السجل دون حالات أو إغلاق أو رسائل أو مهام آلية. تبقى صلاحيات القسم ومسؤول السجل وقواعد لوحة التشغيل كما هي.
- كل هذا مستمد من `D-010` و`D-020` و`D-059`؛ يغيّر هذا التصميم الاسم فقط، ويُبقي الحدود التشغيلية المعتمدة.

## تصميم التسمية المقترح

| العنصر الحالي | الاسم المقترح |
| --- | --- |
| `AftercareService` | `CustomerFollowUpService` |
| `AftercareResource` | `CustomerFollowUpResource` |
| `RentalAftercare` / `ResaleAftercare` | `RentalCustomerFollowUp` / `ResaleCustomerFollowUp` |
| `RentalAftercareActivity` / `ResaleAftercareActivity` | `RentalCustomerFollowUpActivity` / `ResaleCustomerFollowUpActivity` |
| علاقة العميل `aftercare()` | `customerFollowUp()` |
| عناصر قائمة ما بعد الصفقة | «متابعة العميل» / «متابعات العملاء» بحسب المفرد والجمع |
| عمود `مسؤول ما بعد الصفقة` | «مسؤول المتابعة» |
| عمود `متابعة ما بعد الصفقة` في جدول العملاء | «المتابعة القادمة» |
| إجراءات بدء/تسجيل/عرض ما بعد الصفقة | «بدء متابعة العميل»، «تسجيل تواصل»، «سجل متابعة العميل» |
| عدادات لوحة التشغيل | «متابعة العميل — متأخرة» / «متابعة العميل — اليوم» |

تُتبع أسماء الأصناف والملفات الجديدة نمط المشروع (`Rental...`, `Resale...`, `CustomerFollowUp...`) وتُحدّث العلاقات والاستدعاءات والاختبارات القائمة التي تعتمد على الأسماء القديمة. لا تُنشأ واجهة ثانية ولا يتغير ترتيب الأعمدة أو ظهورها الافتراضي.

## توافق التخزين والروابط والتدقيق

- **قاعدة البيانات:** لا تتغير الجداول `rental_aftercare`, `resale_aftercare`, `rental_aftercare_activities`, `resale_aftercare_activities`، ولا العمود `aftercare_id` أو `next_follow_up_at`. تحدد النماذج الجديدة أسماء الجداول وعلاقات المفاتيح القديمة صراحةً. لا يلزم ترحيل أو نقل بيانات.
- **روابط الصفحات:** تستخدم الموارد مسارات جديدة باسم متابعة العميل. يُضاف تحويل من مساري `/admin/rental-aftercares` و`/admin/resale-aftercares` إلى مساريهما الجديدين للمحافظة على الروابط المحفوظة.
- **سجل التدقيق:** لا تُعدّل أو تُحذف الأحداث القديمة. تُعرض مفاتيح `aftercare.started` و`aftercare.activity.recorded` القديمة بالتسميات الجديدة. تكتب العمليات الجديدة مفاتيح `customer_follow_up.started` و`customer_follow_up.activity.recorded`. يدعم عرض نوع السجل أسماء الأصناف القديمة والجديدة لأن أحداث التاريخ تحتفظ بقيمة `subject_type` الأصلية.
- **المستندات:** تُحدّث الوثائق المرجعية الحالية والمسرد والقرار المعتمد. تبقى مستندات `docs/planning-docs/` والسجل الزمني السابق كما كُتبت بوصفها تاريخًا للمشروع؛ لا تُعاد صياغة مصادر قديمة بأثر رجعي.

## النطاق

يشمل نماذج وموارد وصفحات Filament، الخدمة، علاقات العميل والنشاط، صفحة التاريخ، مجموعة إجراءات العميل وCSS المرتبط بها، لوحة التشغيل، أسماء أحداث التدقيق الجديدة وعرض القديم، مسارات الصفحات مع التحويلات، والوثائق المرجعية الحالية والمسرد.

لا يشمل دمج متابعة العميل بمتابعة الطلب، أو بدء المتابعة قبل صفقة ناجحة، أو تغيير الحقول/الصلاحيات/المالكين/التواريخ، أو إعادة تسمية جداول وأعمدة قاعدة البيانات، أو تعديل بيانات سجل التدقيق التاريخية.

## البدائل التي نوقشت

1. **تغيير النصوص الظاهرة فقط:** قليل المخاطر، لكنه يترك أسماء الكود `Aftercare` ويقسم المصطلح بين الواجهة والمنطق؛ لا يطابق طلب المالك بإعادة تسمية المفهوم.
2. **إعادة تسمية المجال في الكود والواجهة والوثائق مع حفظ التخزين الحالي — الموصى به:** يحقق الاسم الموحد، ويترك البيانات ومخططها وروابط الصفحات القديمة قابلة للاستخدام. كلفته تحديث المراجع البرمجية وتعريفات Filament وسجل التوافق.
3. **إعادة تسمية المجال ومخطط قاعدة البيانات:** غير مطلوبة لهذا التغيير، وتضيف مخاطر ترحيل أربعة جداول ومفاتيح أجنبية وأحداث تاريخية دون فائدة تشغيلية مباشرة.

## التحقق وحدود التنفيذ

- لا تُضاف اختبارات ولا تُشغّل اختبارات في هذه المهمة وفق تعليمات التنفيذ السارية. تُحدّث مراجع الاختبارات الموجودة عند إعادة تسمية الأصناف أو المسارات، لكن لا يُدّعى اجتيازها.
- التحقق المسموح بعد التنفيذ: `php -l` لملفات PHP المعدّلة، `php artisan route:list` للتحقق من المسارات الجديدة، تجميع قوالب Blade، وفحص `git diff --check`.
- لا يضاف اعتماد جديد ولا يُعدّل ملف ترحيل سابق. لا يُنشأ commit إلا بطلب صريح من المالك.

## معايير القبول

- تختفي تسمية «ما بعد الصفقة» من الواجهات والوثائق المرجعية الحالية، ويستخدم اسم «متابعة العميل» في القائمة والصفحات والإجراءات ولوحة التشغيل.
- يظهر عمودا جدول العملاء بالاسمين «مسؤول المتابعة» و«المتابعة القادمة» مع بقاء بياناتهما وسلوك إخفائهما/إظهارهما كما هو.
- تعمل بداية السجل عند الصفقة الناجحة، وربط عميل لاحق بصفقة ناجحة، والتسجيل والعرض من صفحة العميل، وتقارير التأخير/اليوم كما كانت.
- تبقى متابعة العميل مستقلة عن متابعة الطلب وتظل محدودة بالقسم وبالعميل ذي الصفقة الناجحة.
- لا تتغير أسماء الجداول أو الأعمدة أو قيم البيانات، وتظل العلاقات والأرقام والتفاعلات التاريخية قابلة للقراءة.
- تفتح المسارات الجديدة، وتحوّل المسارات القديمة إلى الجديدة.
- تعرض أحداث التدقيق القديمة بالمصطلح الجديد دون تعديل سجلاتها، وتكتب الأحداث الجديدة بالمفاتيح الجديدة.
