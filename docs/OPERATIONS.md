# Cible CRM — التشغيل والنسخ والاستعادة

## النسخ الاحتياطي المعتمد

- نسخة قاعدة البيانات يوميًا إلى مخزن متوافق مع S3 خارج خادم التطبيق، مشفرة بـ AES-256، والاحتفاظ بآخر 30 يومًا.
- لا تُرفع ملفات التطبيق أو `.env` ضمن النسخة؛ يشمل النسخ قاعدة البيانات فقط.
- إعدادات النسخ في `config/backup.php` ومخزن الوجهة الخاص `backup_offsite` في `config/filesystems.php`.
- تُشغّل المهام يوميًا بتوقيت القاهرة: النسخ 04:15، التنظيف 04:35، وفحص سلامة النسخة 04:50. الفشل يُسجل في `storage/logs/backups.log`، ويمكن إرسال تنبيهات البريد عند ضبط `BACKUP_ALERT_EMAIL` وبريد Laravel.
- لا تعمل المهام إلا في بيئة production وبعد إعداد كلمة مرور التشفير ومفتاح/سر/اسم مخزن الوجهة. لا تضبط أسرارًا حقيقية في Git أو `.env.example`.

### الإعداد الموصى به مجانًا: Cloudflare R2

R2 متوافق مع S3 وتدعمه إعدادات Laravel الحالية عبر `backup_offsite`. الحصة المجانية الحالية تشمل 10 GB-month تخزينًا و1 مليون عملية Class A و10 ملايين عملية Class B شهريًا، مع نقل بيانات للخارج دون رسوم. الاحتفاظ بثلاثين نسخة يومية يعني أن 10 GB المجانية تكفي تقريبًا إذا كان متوسط النسخة المضغوطة لا يتجاوز 333 MB؛ المساحة التي تتجاوز الحصة تُحاسب حسب السعر الحالي. راجع [أسعار R2 الرسمية](https://developers.cloudflare.com/r2/pricing/) قبل اعتماد توقعات التكلفة.

1. من لوحة Cloudflare، افتح **Storage & databases → R2 → Overview** وأنشئ bucket خاصًا بخطة Standard، مثل `cible-crm-backups`.
2. من **Manage R2 API Tokens** أنشئ token بصلاحية **Object Read & Write**، وقيده على bucket النسخ هذا فقط. يلزم الوصول للقراءة/الكتابة/الحذف حتى تعمل المراقبة وسياسة حذف ما تجاوز 30 يومًا.
3. احتفظ بـ Access Key ID وSecret Access Key فور إنشائهما؛ لن يمكن عرض السر مرة أخرى. خذ Account ID وS3 API endpoint من صفحة R2. صيغة endpoint هي `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`، وregion هو `auto` وفق [إرشادات Cloudflare الرسمية](https://developers.cloudflare.com/r2/get-started/s3/).
4. انسخ `.env.example` إلى `.env` إن لم يكن موجودًا، ثم اضبط `BACKUP_AWS_ACCESS_KEY_ID`, `BACKUP_AWS_SECRET_ACCESS_KEY`, `BACKUP_AWS_BUCKET`, `BACKUP_AWS_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com`, و`BACKUP_AWS_DEFAULT_REGION=auto`. اترك `BACKUP_AWS_URL` فارغًا و`BACKUP_AWS_USE_PATH_STYLE_ENDPOINT=false`، واترك البادئة `BACKUP_AWS_PREFIX=cible-crm`.
5. أنشئ `BACKUP_ARCHIVE_PASSWORD` عشوائية من 32 محرفًا على الأقل، واحفظها خارج المشروع وخارج R2. لا تستخدم قيمة المثال ولا ترسلها في المحادثة.
6. احفظ `.env`، ثم نفّذ `php artisan config:clear` لتحديث الإعدادات. لا تحتاج `config:cache` أثناء اختبار الإعداد المحلي.

يمكن أن يتجاوز حجم النسخ الحصة المجانية: نسخ يومية تبقى 30 يومًا تستهلك تقريبًا مجموع أحجامها. راقب التخزين والفاتورة من لوحة Cloudflare، واضبط تنبيه ميزانية؛ لا تعتمد على كلمة «مجاني» دون قياس الحجم الفعلي.

### إعداد الخادم

1. اتبع إعداد R2 أعلاه، أو جهّز bucket خاصًا في مزود S3-compatible واختر endpoint/region حسب وثائق المزود. امنح بيانات الاعتماد أقل صلاحيات لازمة للكتابة والقراءة والحذف في المسار المخصص.
2. اضبط متغيرات `BACKUP_AWS_ACCESS_KEY_ID`, `BACKUP_AWS_SECRET_ACCESS_KEY`, `BACKUP_AWS_DEFAULT_REGION`, `BACKUP_AWS_BUCKET`, `BACKUP_AWS_ENDPOINT`, `BACKUP_AWS_USE_PATH_STYLE_ENDPOINT`, و`BACKUP_AWS_PREFIX`. اترك `BACKUP_AWS_ENDPOINT` فارغًا لمزود AWS القياسي.
3. أنشئ `BACKUP_ARCHIVE_PASSWORD` عشوائية لا تقل عن 32 محرفًا وخزّنها منفصلة عن مخزن النسخ، في مدير أسرار أو خزنة مؤسسية؛ فقدانها يمنع فك النسخ المشفرة. لن تعمل المهام المجدولة دون كلمة المرور، ودعم AES-256، وبيانات وجهة التخزين.
4. اضبط `BACKUP_ALERT_EMAIL` وتهيئة البريد إن أردت التنبيهات. حدد `DB_DUMP_BINARY_PATH` إلى مجلد `mysqldump`؛ في XAMPP على Windows يكون عادة `E:\xampp\mysql\bin`.
5. فعّل Laravel scheduler على الخادم. على Linux أضف cron يشغّل `php /path/to/project/artisan schedule:run` كل دقيقة. على Windows Server أنشئ مهمة مجدولة كل دقيقة لتشغيل `php.exe` مع وسيط `artisan schedule:run` ومجلد المشروع كـ working directory.
6. راقب `backup:monitor` وسجل `storage/logs/backups.log`، وتحقق دوريًا من وصول الملفات إلى الوجهة. إنشاء archive وحده لا يثبت إمكانية الاستعادة.

### التشغيل اليدوي والفحص

بعد ضبط بيئة تشغيل آمنة، يمكن استخدام `php artisan backup:run --only-db` لإنشاء نسخة، و`php artisan backup:clean` لتطبيق سياسة الثلاثين يومًا، و`php artisan backup:monitor` لفحص العمر والحجم. لا تستخدم `backup:run` على بيئة التطوير الحالية قبل ضبط وجهة خارجية فعلية، حتى لا تُرسل نسخة بيانات حقيقية إلى مخزن غير مقصود.

## اختبار الاستعادة

1. نزّل نسخة إلى بيئة معزولة، ولا تستعد فوق قاعدة الإنتاج أو قاعدة التطوير الحالية.
2. فك تشفير archive بكلمة المرور المحفوظة في مدير الأسرار، ثم استعد dump قاعدة البيانات إلى قاعدة مؤقتة جديدة بصلاحيات محدودة.
3. شغّل التطبيق مؤقتًا على قاعدة الاستعادة، وافحص الجداول والعلاقات وسجلات الدخول، ثم شغّل `php artisan migrate:status`.
4. وثّق تاريخ النسخة ونتيجة الاستعادة والمدة، ثم احذف قاعدة الاختبار والملفات المؤقتة بأمان.

اختبار الاستعادة الدورية مسؤولية مشغل النظام. في 2026-10-25 أُنشئ أول backup فعلي مشفر من قاعدة التطوير إلى bucket `cible` في Cloudflare R2؛ أظهر `backup:list` أن الوجهة reachable والنسخة healthy بحجم يقارب 10.19 KB. هذا يثبت إعداد الاعتماد والرفع والفحص فقط؛ لم تُجرَ استعادة فعلية بعد، ويلزم اختبارها في قاعدة مؤقتة معزولة. أُصلح ربط أحداث إشعارات الحزمة بعد أن كشفت التجربة الأولى نقصًا في إعدادها.

## متطلبات نشر أخرى

- استخدم حساب قاعدة بيانات مخصصًا للتطبيق بصلاحيات الحد الأدنى، واضبط `APP_ENV=production` و`APP_DEBUG=false`، واحفظ `APP_KEY` وبيانات الاتصال خارج المستودع.
- فرض HTTPS، واستخدم cookies آمنة، وقيّد الوصول إلى لوحة الإدارة على مستوى الخادم عند توفر ذلك.
- تجنب نسخ `.env` أو ملفات رفع المستخدمين إلى وجهة النسخ ما لم تعتمد سياسة منفصلة؛ الإعداد الحالي يحمي قاعدة البيانات فقط.
- تُؤرشف سجلات العملاء والمناطق فقط مع الاحتفاظ بعلاقات الطلبات التاريخية، ويمكن استعادتها بواسطة المدير. لا يوجد حذف نهائي أو دمج؛ العناصر المؤرشفة لا تظهر للاستخدام في طلبات جديدة.
