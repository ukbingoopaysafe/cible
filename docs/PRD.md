# Cible Real Estate CRM — متطلبات المنتج

**الحالة:** وثيقة المتطلبات المرجعية. المتطلبات المعتمدة فقط هي الملزمة.  
**آخر تحديث:** 2026-10-24

## 1. تعريف المنتج والمستخدمون

Cible تطبيق ويب داخلي لإدارة علاقات العملاء ودورات طلب الإيجار وإعادة البيع والمتابعات والصفقات واستمرار العلاقة بعد الصفقة.

المستخدمون المعتمدون:

- موظف إيجار.
- موظف إعادة بيع.
- مدير الشركة.

لا تُضاف أدوار أخرى قبل اعتمادها. يمكن تعيين الموظف صراحةً في قسم واحد أو القسمين (`D-034`). المندوب الميداني بيانات مشاركة بلا حساب دخول في الإصدار الأول (`D-039`). تصنيف صلاحيات الحقول يظل مفتوحًا في [`DECISIONS.md`](./DECISIONS.md).

| `PRD-008` | استمرار العلاقة بعد الصفقة وظيفة مستقلة عن متابعة الطلب الجاري داخل القسم نفسه، ويظل مرتبطًا بسجل العميل في ذلك القسم. | `A` | لا توجد علاقة aftercare مشتركة بين القسمين، ولا تتحول متابعة ما بعد الصفقة إلى متابعة طلب مفتوح. |
| `PRD-009` | مدير الشركة يستطيع قراءة/عرض قسمي الإيجار وإعادة البيع وعملياتهما، دون بحث عميل موحّد يدمج السجلين. | `A` | يتمتع بصلاحيات كاملة داخل القسم/الأقسام المصرح بها وفق `D-040`، مع بقاء عزل الأقسام والضوابط الخاصة في `D-026` و`D-027` نافذة. |
| `PRD-010` | تُفرض قيود الأقسام في الـ backend وطبقة الوصول إلى البيانات، وليس بإخفاء عناصر الواجهة فقط. | `A` | يشمل ذلك سجلات العملاء والبحث والروابط المباشرة وواجهات API والتقارير والتصدير والسجلات المرتبطة والمؤشرات. |
| `PRD-011` | تُسجل بيانات الوحدة/العقار فقط بالقدر اللازم لدعم طلب أو ترشيح أو معاينة أو صفقة. | `A` | لا يوجد كتالوج أو مخزون أو شاشة إدارة وحدات. الحد الأدنى للحقول `Q-005`. |
| `PRD-012` | شروط العمولة تختلف حسب الصفقة والأطراف، ولا توجد نسبة أو قيمة افتراضية ثابتة. | `A` | لا يُصمم النظام كأن كل صفقة لها نسبة واحدة. يسجل الاتفاق فقط دون حالة سداد أو تحصيل (`D-037`)؛ تفاصيل حقول الاتفاق `Q-006`. |
| `PRD-013` | لا يُحصر وصف إعادة البيع في طلبات المشترين؛ إجابة المالك تذكر المشترين والمالكين البائعين، وتُسجل بيانات المالك البائع داخل الصفقة عند الحاجة فقط. | `A` للمفهوم والحدود | لا تُنشأ قاعدة ملاك أو Listing داخل Cible. لا يوجد طلب بائع مستقل في الإصدار الأول؛ بيانات البائع داخل سياق الصفقة عند الحاجة فقط (`D-035`). |
| `PRD-014` | يمكن تسجيل كود الوحدة في تطبيق Listing الخارجي عند الحاجة، بدون تكامل معه في الإصدار الأول. | `A` | لا يُفترض أن كل وحدة مسجلة هناك. يصف المصدر `S-013` الكود بأنه رقمي؛ وتفاصيل بيانات الوحدة وشرط/صيغة الكود تبقى `Q-005`. |
| `PRD-015` | التقنية المعتمدة: Laravel + MySQL + Filament، وواجهة عربية RTL متجاوبة على سطح المكتب والهاتف. | `A` | لا تُستبدل التقنية دون قرار موثق. |
| `PRD-016` | النطاق CRM فقط، وتُستبعد إدارة العقارات والصيانة والمحاسبة والتحصيل والقوائم المستقلة والتكاملات غير المعتمدة. | `A` | راجع [`PROJECT_CONTEXT.md`](./PROJECT_CONTEXT.md). |
| `PRD-017` | يرى الموظف سجلات عملاء قسمه والطلبات الظاهرة داخل نطاقه القسمي المصرح به، وليس فقط العملاء الذين يملكهم. | `A` | لا يعني ذلك تجاوز قيود الحقول أو الوصول إلى سجلات القسم الآخر؛ لا يوجد بحث أو Link بين سجلات العملاء (`D-020`). |
| `PRD-018` | لا تُفرض قائمة شاشات ثابتة؛ تُصمم الشاشات والتنقل حول مسارات العمل المؤكدة. | `A` | قائمة الشاشات الخمس تبقى مقترحًا مصدريًا. |
| `PRD-019` | لا يوجد ملف عميل مشترك أو بحث عميل موحّد بين القسمين. لكل قسم سجلات عملاء ووسطاء مستقلة، وتبقى طلباتهم وأنشطتهم ومتابعاتهم وصفقاتهم وaftercare مستقلة داخل القسم. يجوز وجود سجلين منفصلين للشخص نفسه في القسمين، ولا يصل موظف قسم إلى سجلات القسم الآخر، ولا يوجد deduplication أو linking أو synchronization أو تحديث متبادل بينهما. | `A` | يسري على البحث والقوائم ولوحات المعلومات والتقارير والتصدير والروابط المباشرة وAPI وتتبّع العلاقات والعدادات (`D-020`، `D-025`، `D-026`). المدير يقرأ القسمين بشكل منفصل، ويتمتع بصلاحيات كاملة داخل كل قسم مُصرح به وفق `D-040`؛ تظل ضوابط الوسيط والتدقيق وإعادة التعيين في `D-026` و`D-027` نافذة. |
| `PRD-020` | يبقى Laravel + MySQL + Filament تطبيقًا واحدًا وقاعدة واحدة؛ لا تطبيقات أو سيرفرات أو قواعد MySQL فيزيائية منفصلة دون اعتماد مالك لاحق. | `A` | الفصل المطلوب معماري وتشغيلي داخل التطبيق، وليس فصل بنية تشغيل. |
| `PRD-021` | الإصدار الأول يشمل استيراد بيانات من Excel إلى CRM وتصدير بيانات من CRM إلى Excel. | `A` | القدرة `D-021`. النطاق التفصيلي `D-023`: استيراد عملاء القسم بإنشاء فقط؛ تصدير العملاء والطلبات الظاهرة داخل القسم؛ بلا صفقات/عمولات/تفريغ أنشطة. تفاصيل الاستيراد `D-024`؛ الحقول `Q-004`/`Q-024` والتفاصيل المتبقية `Q-025`. لا يتجاوز عزل الأقسام (`D-006`، `D-020`). |
| `PRD-022` | الإصدار الأول يشمل زر فتح محادثة WhatsApp إذا كانت بيانات الاتصال اللازمة متاحة، وإمكانية تسجيل التواصل داخل CRM عبر نظام الأنشطة/سجل التواصل. | `A` | فتح المحادثة وتسجيل التواصل فقط (`D-022`). خارج النطاق: WhatsApp Business API، والإرسال/الاستقبال الآلي، ومزامنة المحادثات. الرابط وصيغة الرقم وغياب الرقم `Q-026`؛ حقول التسجيل وربط الطلب `Q-027`. |
| `PRD-023` | العميل النهائي والوسيط وجهة الاتصال أشخاص/مفاهيم مختلفة؛ جهة الاتصال هي من يخاطبه الموظف وقد تكون العميل أو الوسيط، وهي منفصلة كذلك عن مصدر الوصول ومسؤول الطلب. يجوز استقبال طلب عبر وسيط في أي قسم قبل معرفة العميل، وتسجيل أنشطته ومتابعاته، ثم ربط العميل المكتشف بالطلب نفسه مع حفظ التاريخ. يمكن للوسيط أن يرتبط بطلبات مستقلة متعددة داخل قسمه، وتظل سجلاته معزولة بين القسمين. | `A` | سلوك العمل `D-025`؛ الحقول والتمثيل المادي `Q-001`، `Q-004`، `Q-028`. لا تُنشأ هوية عميل وهمية ولا يُعرض المجهول كحقيقة. |
| `PRD-024` | تُدار سجلات الوسطاء مستقلًا داخل كل قسم: أي موظف مخول بالقسم يمكنه تعديل سجل الوسيط، وكل تعديل مدقق، ولا مالك ثابتًا للوسيط؛ لكل طلب مسؤول مستقل. يمنع افتراضيًا إنشاء وسيط آخر برقم موبايل مطابق مطبع في القسم، مع توجيه الموظف لمراجعة السجل. تشابه الاسم وحده لا يثبت التكرار؛ يُحذر من الاحتمال ويسمح بالمتابعة بعد المراجعة، وكذلك عند غياب الرقم بحسب البيانات المتاحة. حذف الوسيط دائم للمدير فقط، ويحظر عند وجود طلب نشط إلى أن يغلقه المدير أو يعيد تعيينه يدويًا لوسيط آخر؛ تعرض هوية الوسيط وأعداد الطلبات والأنشطة وتحذير اللااستعادة، ويطلب سبب إلزامي، مع حفظ السياق التاريخي. | `A` | `D-026`؛ تعريف الطلب النشط `Q-021`، الاستثناء للرقم المشترك `Q-030`، وإدخال الهاتف/تطبيعه `D-029`. لا تجاوز لتكرار رقم الموبايل معتمد. |
| `PRD-025` | سجل التدقيق المحمي يسجل تغييرات الوسطاء وإعادة التعيين، ويحتوي على الأقل المنفذ والوقت ونوع العملية وما تغير. المدير يرى كامل السجل، والموظف يرى ما أجراه بنفسه؛ لا يجوز للمستخدمين تعديل أو حذف المدخلات. إعادة التعيين تتطلب سببًا: الموظف يطلبها إلى موظف بالقسم نفسه ويظل المسؤول الحالي حتى قرار المدير، والمدير يقبل/يرفض أو يعيد التعيين مباشرة إلى موظف بالقسم نفسه. عند التنفيذ تسري فورًا بلا قبول من المسؤول الجديد، وتنتقل الأعمال المستقبلية مع إبقاء الأنشطة المكتملة ومنفذيها في السجل؛ يسجل التدقيق الأطراف والسبب والقرار والأوقات. | `A` | `D-027`. نطاق التدقيق الكامل والاحتفاظ وأمن التنفيذ `Q-013`؛ إلغاء الطلب المعلق وحالة المدير لنفسه `Q-031`. |

| `PRD-026` | داخل القسم الواحد، يمنع إنشاء سجل عميل جديد عند تطابق رقم الهاتف بعد توحيد تنسيقه مع سجل قائم، ويوجه الموظف إلى السجل الموجود. عند تشابه الاسم أو بيانات أخرى دون تطابق الهاتف، يظهر تحذير احتمال تكرار ويسمح بالاستمرار بعد المراجعة. لا يحدث دمج تلقائي، ولا مطابقة أو ربط بين سجلات قسمي الإيجار وإعادة البيع. | `A` | `D-028`. |
| `PRD-027` | إدخال الهاتف والتحقق منه: مصر هي الدولة الافتراضية ويمكن اختيار دولة أخرى؛ يُقبل الرقم المصري المحلي دون مفتاح الدولة وفق قواعد مصر؛ عند اختيار دولة أخرى يظهر مفتاحها ويُقبل إدخال/لصق الرقم كاملًا بالمفتاح الدولي. إذا تعارض المفتاح الدولي الملصوق مع الدولة المختارة، يطلب النظام تأكيد تغيير الدولة ولا يغيّرها بصمت. تُقبل الصيغ المحلية والدولية الصحيحة وتُوحّد قبل الحفظ وفحص التكرار، دون تخمين الدولة. يُمنع الحفظ عند رقم غير صالح/غير مكتمل أو تعذّر التحقق تقنيًا حتى ينجح التحقق. صحة الصيغة لا تثبت فعالية الرقم أو ملكيته للشخص. | `A` | `D-029`؛ اختيار مكتبة بعينها ورسائل الواجهة وتفاصيل التنفيذ والاختبارات أعمال تقنية قبل التنفيذ. |
| `PRD-028` | يتكون الحد الأدنى لملف العميل في كل قسم من الاسم ورقم الهاتف الإلزاميين والجنسية الاختيارية. تُخزن تفاصيل احتياج العميل ومواصفاته في الطلب لا في ملف العميل؛ يمكن أن يكون للعميل أكثر من طلب عبر الوقت داخل القسم. | `A` | `D-030`. حقول الطلب التفصيلية في `Q-004`، ولا توجد حقول مشتركة بين قسمي الإيجار وإعادة البيع (`D-020`). |
| `PRD-029` | في طلب الإيجار، المنطقة المطلوبة إلزامية عند الإنشاء؛ يمكن أن يُسجل الطلب عبر وسيط قبل معرفة العميل النهائي؛ الميزانية المعلنة والميزانية المستهدفة حقلاّن منفصلان اختياريان، ومدة الإيجار والملاحظات العامة اختياريتان عند الإنشاء. | `A` | `D-031`. بقية حقول الإيجار والمراحل والحالات والنتائج، وكذلك تفاصيل طلب إعادة البيع، تبقى في `Q-004`. |
| `PRD-030` | تُختار منطقة طلب الإيجار من قائمة مُدارة تمنع التكرار. يستطيع المدير منح/سحب صلاحية إضافة المناطق لموظف محدد؛ الموظف المخوّل فقط يستطيع إضافة مناطق، بينما يستطيع المستخدمون الآخرون اختيار الموجود فقط. | `A` | `D-032`. القيم الفعلية للمناطق لم تُحسم؛ سجل التدقيق والأرشفة/التعطيل عند الاستخدام مقترحان فقط في `P-015` و`P-016`. |
| `PRD-031` | يحتوي طلب الإيجار وطلب إعادة البيع على حقل محافظة مستقل، وتُختار المنطقة من قائمة مرتبطة بالمحافظة المختارة. المحافظات المبدئية المعتمدة هي القاهرة والجيزة، ولا يمكن اختيار منطقة تابعة لمحافظة أخرى. | `A` | `D-033`. القيم الفعلية للقائمة الكاملة للمناطق وسياسة دورة حياتها لم تُحسما بعد (`Q-004`، `Q-016`). |

### قواعد التنظيف المقترحة

- «الكل المنطقة» خيار واجهة لعرض كل المناطق، وليس قيمة منطقة.
- تُعرض «مدينة نصر» مرة واحدة فقط؛ لا تُقسم إلى شرق/غرب في الإصدار الأول دون قرار مالك، رغم التمييز الإداري الرسمي بينهما.
- «عباس العقاد» يُكتب في الملاحظات تحت مدينة نصر، لا كخيار مستقل.
- «شارع شهاب بالمهندسين» يُكتب في الملاحظات تحت المهندسين.
- «ناصر الثورة بفيصل» يُكتب في الملاحظات تحت فيصل.
- «ميدان المساحة» يُكتب في الملاحظات، لا كخيار مستقل.
- «البحر الأعظم» يُكتب في الملاحظات، لا كخيار مستقل؛ خيار «الجيزة» العام يظل قيد الدراسة (Q-032).
- لا تظهر «المعادي» تحت الجيزة ولا تتكرر في القائمتين.
- القائمة تعكس مناطق تشغيلية يحتاجها الفريق، ولا تحاول محاكاة كل تقسيم إداري رسمي. توثيق المصدر الجغرافي لا يعني اعتماد القائمة من المالك.

لا يُنفذ dropdown نهائي ولا تُغلق Q-004 وQ-032 قبل اعتماد المالك للقائمة كاملة، بما في ذلك قرار «الجيزة» كمنطقة عامة، وطريقة عرضها دون لبس مع حقل المحافظة.

## 6. Excel وWhatsApp في الإصدار الأول

القدرة الوظيفية معتمدة. تفاصيل التنفيذ أدناه ليست قرارات، ولا تُنفَّذ بالتخمين.

### 6.1 استيراد وتصدير Excel

**الحالة:** `A` للقدرة (`PRD-021`، `D-021`) وللنطاق (`D-023`) ولتفاصيل الاستيراد (`D-024`). الحقول `Q-001`، `Q-004`، `Q-024`؛ التفاصيل المتبقية وحدود الملف الرقمية `Q-025`.

ما حُسم (`D-021`، `D-023`):

- الاستيراد والتصدير جزء من الإصدار الأول. Excel ليس بديلًا عن قاعدة CRM، ولا توجد مزامنة مستمرة.
- الاستيراد: سجلات العملاء داخل القسم المصرح به فقط؛ إنشاء سجلات جديدة فقط؛ لا استيراد لطلبات أو أنشطة أو صفقات أو عمولات؛ لا تحديث عبر المطابقة ضمن هذا النطاق.
- التصدير: سجلات العملاء والطلبات التي يحق للمستخدم قراءتها داخل قسمه. لا صفقات ولا عمولات ولا تفريغ أنشطة كامل في هذه المرحلة.
- موظف القسم أو المدير يستورد إلى القسم/الأقسام المصرح بها فقط، مع الالتزام بنطاق العملاء والإنشاء فقط (`D-023`، `D-040`).
- لا مطابقة أو ربط أو كشف أو مزامنة عبر القسمين (`D-006`، `D-017`، `D-020`، `D-021`).
- لا تُخترع حقول؛ القالب يُشتق بعد `Q-001` و`Q-004`. لا يُفترض أن ملفات Excel الحالية مطابقة لنموذج البيانات.

تفاصيل الاستيراد المعتمدة (`D-024`): يقبل النظام `.xlsx` فقط وينفذ استيرادًا جزئيًا؛ تنشأ سجلات العملاء للصفوف الصالحة فقط، وتُترك الصفوف الفاشلة دون إنشاء. يفحص الملف والصفوف، ويوضح أخطاء التحقق وأرقام الصفوف، ويعرض أعداد النجاح والفشل ويوفر تقريرًا قابلًا للتنزيل بالصفوف الفاشلة وأسبابها. يمكن تصحيح الصفوف الفاشلة وإعادة استيرادها دون الصفوف الناجحة. يظل الإنشاء فقط نافذًا؛ لا تحديث لسجل موجود بالمطابقة. تُوضح التكرارات القابلة للاكتشاف دون اختراع معيار مطابقة؛ سياسة منع التكرار داخل القسم معتمدة في `D-028`، وقواعد إدخال/تحقق/توحيد الهاتف معتمدة في `D-029`. لا حد رقمي معتمد لحجم الملف أو عدد الصفوف حاليًا.

ما لم يُحسم: حقول القالب (`Q-024` بعد `Q-001`/`Q-004`)؛ حدود الملف الرقمية وأي تفاصيل أخرى لا يمكن حسمها قبل إجابة الأسئلة السابقة (`Q-025`)؛ سياسة منع التكرار داخل القسم معتمدة في `D-028`؛ قواعد إدخال/تحقق/توحيد الهاتف معتمدة في `D-029`؛ حقول العمولة (`Q-006`)؛ تفاصيل إدارة القوائم المرجعية والعمليات المقيدة صراحةً، إن وجدت، وفق القرارات والأسئلة ذات الصلة.

`P-008` اعتبار معماري غير معتمد، ولا يشكل `D-024` موافقة على طريقة تنفيذ تقنية بعينها. `P-009` تاريخي `SUP` بعد `D-023`، و`P-010` تاريخي `SUP` بعد `D-024`.

### 6.2 WhatsApp: فتح المحادثة وتسجيل التواصل

**الحالة:** `A` للقدرة (`PRD-022`، `D-022`)؛ التفاصيل `Q-026` و`Q-027`.

ما حُسم:

- زر فتح محادثة إذا كانت بيانات الاتصال اللازمة متاحة.
- إمكانية تسجيل التواصل داخل CRM باستخدام نظام الأنشطة/سجل التواصل، لا بكيان محادثة WhatsApp مستقل غير معتمد.
- خارج النطاق: WhatsApp Business API، إرسال/استقبال آلي، مزامنة سجل المحادثات.
- الزر وتسجيل التواصل لا يكشفان سجل عميل أو طلب أو رقم من القسم الآخر (`D-020`).
- فتح المحادثة لا يغني عن تاريخ المتابعة القادمة للطلب النشط (`D-008`).
- وجود حقل هاتف وتصنيفه داخل سجل العميل يبقى `Q-001`؛ لا يُخترع حقل تواصل لأجل الزر قبل ذلك.

ما لم يُحسم: بناء الرابط، صيغ الأرقام، سلوك الرقم الغائب/غير الصالح، الحقول المطلوبة عند التسجيل، هل التسجيل يدوي بالكامل أم تُمرَّر بيانات من واجهة WhatsApp، وربط السجل بالطلب عند تعدد الطلبات.

### 6.3 خارج النطاق المعتمد حاليًا

**الحالة:** `DEF` ما لم يُعتمد لاحقًا.

- تكامل WhatsApp Business API.
- إرسال أو استقبال الرسائل آليًا.
- مزامنة سجل محادثات WhatsApp مع CRM.
