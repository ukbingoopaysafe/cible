# Cible CRM — مخطط الإصدار الأول المقترح

**الحالة:** مقترح عمل للمراجعة، وليس مواصفات تنفيذ نهائية. تم تحديثه ليعكس قرارات المالك بتاريخ 2026-10-24؛ الأسئلة المفتوحة ما زالت حاكمة.
**آخر تحديث:** 2026-10-24  
**الغرض:** تحويل القرارات والمواد المصدرية الموجودة إلى مخطط واحد قابل للمراجعة، وتقليل الرجوع المتكرر إلى الوثائق المتفرقة.
**المرجع الحاكم:** لا يغيّر هذا المستند `DECISIONS.md`؛ عند التعارض يُقدّم القرار المعتمد، وتظل أي نقطة غير محسومة مفتوحة.
**النطاق:** CRM فقط، باستخدام Laravel + MySQL + Filament، في تطبيق واحد وقاعدة واحدة، مع فصل تشغيلي وصلاحيّاتي بين الإيجار وإعادة البيع.

## 1. المبادئ الثابتة التي لا يعيد هذا المقترح فتحها

- لا Listing أو مخزون عقارات أو إدارة أملاك أو صيانة أو محاسبة أو تحصيل.
- بيانات العملاء والوسطاء والطلبات والأنشطة والمتابعات والصفقات معزولة بين الإيجار وإعادة البيع؛ لا مشاركة أو ربط أو بحث أو deduplication بين القسمين.
- الاسم والهاتف إلزاميان في سجل العميل، والجنسية اختيارية. تفاصيل احتياج العقار تحفظ في الطلب لا ملف العميل.
- يمكن إنشاء طلب عبر وسيط قبل معرفة العميل النهائي، ثم ربط العميل بالطلب نفسه دون فقد الأنشطة.
- كل طلب نشط له موعد متابعة قادم. النشاط الذي حدث منفصل عن مهمة/موعد المتابعة القادم.
- طلب الإيجار يتطلب المحافظة والمنطقة عند الإنشاء؛ الميزانية المعلنة والمستهدفة منفصلتان واختياريتان، ومدة الإيجار والملاحظات العامة اختياريتان.
- لا توجد عمولة افتراضية؛ الاتفاق يختلف حسب الصفقة والأطراف.
- Excel: استيراد عملاء بإنشاء فقط وملف `.xlsx`، مع تقرير أخطاء صفوف وإمكانية إعادة المحاولة؛ التصدير للسجلات التي يحق للمستخدم رؤيتها. WhatsApp: فتح المحادثة وتسجيل النشاط يدويًا، دون API أو مزامنة.
- هذه المبادئ مستندة إلى القرارات في `DECISIONS.md`، خصوصًا `D-008`, `D-020`–`D-033`. راجع السجل عند الحاجة إلى نص القرار الكامل.

## 2. مخطط البيانات المقترح

### 2.1 سجلات منفصلة لكل قسم

| المفهوم | الإيجار | إعادة البيع | الحالة |
|---|---|---|---|
| العميل | سجل عميل إيجار | سجل عميل إعادة بيع | الفصل معتمد؛ الحقول الأساسية معتمدة |
| الطلب | طلب إيجار | طلب إعادة بيع | كيان منفصل عن العميل والصفقة؛ الحقول والحالات غير مكتملة الاعتماد |
| الوسيط | وسيط الإيجار | وسيط إعادة البيع | سجل منفصل لكل قسم |
| النشاط/التواصل | نشاط داخل القسم | نشاط داخل القسم | النشاط المنجز منفصل عن المتابعة القادمة |
| المتابعة القادمة | موعد/مهمة مرتبطة بسياق القسم | موعد/مهمة مرتبطة بسياق القسم | يجب استيفاء موعد للطلب النشط؛ شكل الكيان المادي ما زال تصميمًا |
| ترشيح/معاينة | سياق وحدة مرتبط بالطلب | سياق وحدة مرتبط بالطلب | لا كتالوج وحدات |
| الصفقة | صفقة إيجار | صفقة إعادة بيع | الحقول وعلاقة العدد بالطلب تحتاج حسمًا |
| علاقة ما بعد الصفقة | علاقة داخل قسم الإيجار | علاقة داخل قسم إعادة البيع | مستقلة عن follow-up الطلب، وتفاصيلها مفتوحة |

**توصية تقنية:** يفضل أن تكون حدود القسم واضحة في نماذج البيانات والخدمات والسياسات والاختبارات، لا مجرد فلترة واجهة. يمكن مشاركة كود تقني داخلي عند الحاجة، لكن لا تُشارك سجلات العميل أو الوسيط أو علاقاتهم بين القسمين. الشكل النهائي للجداول والمفاتيح لا يعتمد قبل حسم `Q-028`؛ حُسم حد صفقة واحدة لكل طلب في `D-036`، وعدم وجود طلب بائع مستقل في `D-035`.

### 2.2 سجل العميل

| الحقل | المقترح | الحالة |
|---|---|---|
| الاسم | إلزامي | معتمد `D-030` |
| الهاتف | إلزامي، تحقق وتطبيع قبل الحفظ | معتمد سلوكيًا `D-029` |
| الجنسية | اختياري | معتمد `D-030` |
| ملاحظات العميل | لا تضاف افتراضيًا | توصية لتقليل البيانات؛ تحتاج مراجعة عند تصميم الحقول |

لا تُحفظ مواصفات العقار أو ميزانيات الطلب في ملف العميل. لا يوجد دمج تلقائي. عند تطابق الهاتف بعد التطبيع داخل القسم، يمنع إنشاء عميل مكرر؛ تشابه الاسم وحده ينتج تحذيرًا لا منعًا.

| جهة الاتصال | الشخص الذي يتواصل معه الموظف؛ قد يكون العميل أو الوسيط | المفهوم معتمد؛ التمثيل المادي `Q-028` |
| الوسيط | اختياري | المفهوم معتمد؛ التمثيل المادي `Q-028` |

| مصدر الوصول | منفصل عن الوسيط والمسؤول | الانفصال معتمد؛ قائمة قابلة للإدارة مع «أخرى» وملاحظة اختيارية (`D-038`)؛ القيم الابتدائية `Q-011` |
| المحافظة والمنطقة | إلزاميتان عند الإنشاء؛ المنطقة من قائمة مرتبطة بالمحافظة | المحافظة `D-033`؛ القائمة النهائية `Q-032` |

| الميزانية المعلنة | اختيارية | `D-031` |
| الميزانية المستهدفة بعد التأهيل | اختيارية ومنفصلة عن المعلنة | `D-031` |
| العملة وفترة الميزانية | لا تفترض قيمة افتراضية | `Q-004` |
| ملاحظات الطلب | اختيارية | `D-031` |
| الحالة والمرحلة والنتيجة | قائمة منفصلة لكل قسم، تُعتمد لاحقًا | `Q-004` |
| المتابعة القادمة | مطلوبة ما دام الطلب نشطًا | `D-008`; تعريف النشط `Q-021` |

### 2.4 طلب إعادة البيع — مسودة حد أدنى للمراجعة

المصادر الحالية تثبت مسار طلب إعادة البيع للمشتري، وتسمح ببيانات مالك بائع داخل الصفقة فقط؛ لكنها لا تكفي لاعتماد كل الحقول. لذلك، هذه مسودة مراجعة وليست متطلبًا نهائيًا:

- العميل النهائي/جهة الاتصال/الوسيط/مصدر الوصول/المسؤول وفق الفصل المفاهيمي نفسه، لكن داخل نطاق إعادة البيع فقط.
- غرض الطلب: شراء أو احتياج آخر يوافق عليه المالك؛ لا يوجد طلب بائع مستقل في الإصدار الأول (`D-035`).
- الموقع/المنطقة، نوع الوحدة، الميزانية، المساحة، ومتطلبات أخرى كحقول مرشحة مستندة إلى وصف المصدر.
- المحافظة والمنطقة في طلب إعادة البيع وفق مبدأ `D-033`، مع اعتماد قائمة المناطق النهائية قبل تنفيذها.
- الحالة والمرحلة والنتيجة والمتابعة القادمة وفق سياسة القسم؛ القيم النهائية `Q-004`.
- كود وحدة خارجي اختياري فقط عند الحاجة؛ لا تكامل مع تطبيق Listing (`D-016`).

### 2.5 الوحدة والصفقة والعمولة

- تحفظ بيانات الوحدة فقط بالقدر اللازم للتعرف عليها داخل الترشيح أو المعاينة أو الصفقة، لا كيان مخزون مستقل.
- **قرار معتمد:** صفقة واحدة كحد أقصى لكل طلب (`D-036`). لا يعني ذلك أن كل طلب ينشئ صفقة.
- اتفاق العمولة يرتبط بالصفقة ويصف الطرف/الأطراف والشروط والقيمة/الطريقة بحسب الاتفاق؛ لا نسبة افتراضية. تسجيل اتفاق العمولة فقط دون حالة سداد أو تحصيل (`D-037`)؛ تفاصيل حقول الاتفاق `Q-006`.
- بيانات المالك البائع تظل داخل سياق الصفقة وفق `D-015` وفق قرار عدم وجود طلب بائع مستقل في الإصدار الأول (`D-035`).

## 3. مسار العمل المقترح

### 3.1 الطلب قبل معرفة العميل
1. إنشاء طلب في القسم الصحيح، مع وسيط/جهة اتصال إذا كانت معلومة.
2. تعيين مسؤول الطلب ومصدر الوصول كلٌّ في حقله.
3. تحديد المنطقة المطلوبة للإيجار، وتحديد موعد المتابعة القادم قبل إبقاء الطلب نشطًا.
4. تسجيل التواصل والنتيجة كأنشطة، دون إنشاء هوية عميل وهمية.
5. عند معرفة العميل، إنشاء/اختيار سجل العميل داخل القسم وربطه بالطلب القائم مع حفظ التاريخ.

### 3.2 متابعة الطلب
1. تسجيل النشاط المنجز (وقت/قناة/ملخص/نتيجة) منفصلًا عن موعد المتابعة القادم.
2. تحديث الاحتياجات دون محو الميزانية المعلنة؛ تحفظ الميزانية المستهدفة منفصلة.
3. تسجيل الترشيحات والمعاينات كبيانات سياقية مرتبطة بالطلب.
4. بعد المعاينة، تسجيل النتيجة والملاحظات وتحديد الخطوة التالية.
5. لا تُغلق المرحلة أو النتيجة النهائية بقيم غير معتمدة؛ حالات الطلب ما زالت `Q-004`.

### 3.3 إغلاق الطلب والصفقة
1. لا تُنشأ الصفقة إلا وفق قاعدة الإغلاق التي سيعتمدها المالك.
2. تسجل بيانات الوحدة والسعر المتفق عليه والأطراف وشروط العمولة في سياق الصفقة بالقدر المطلوب.
3. يبقى الطلب والصفقة كيانين منفصلين.
4. لا يُفرض سبب إغلاق أو حالة تحصيل قبل اعتماد قواعده.

### 3.4 ما بعد الصفقة
- متابعة ما بعد الصفقة مسار منفصل عن follow-up الطلب قبل الإغلاق.
- ترتبط العلاقة بعميل القسم نفسه؛ لا توجد علاقة مشتركة بين الإيجار وإعادة البيع.
- **توصية للمراجعة:** تبدأ العلاقة بعد إغلاق صفقة ناجحة، ويُحدد مسؤول وموعد تواصل لاحق عند الحاجة. قواعد البدء والانتهاء والتوقيت التفصيلية تظل `Q-007` و`Q-022`.

## 4. الصلاحيات — خط أساس مقترح

- الوصول إلى كل قسم يمنح صراحةً لكل مستخدم؛ وجود وصول للقسمين لا يخلق أي ربط بين بياناتهما.
- الموظف يرى سجلات القسم المصرح به وفق `D-017`، وليس فقط سجلاته الخاصة.
- لا تمنح القراءة صلاحية التعديل أو الحذف.
- التعديلات الحساسة (الوسيط، إعادة تعيين الطلب، إدارة المناطق) تتبع القرارات المسجلة في `D-026`, `D-027`, `D-032`.
- المدير يملك صلاحيات كاملة داخل القسم/الأقسام المصرح بها (`D-040`)، مع بقاء عزل الأقسام والضوابط الخاصة نافذة.
- المندوب الميداني لا يملك حساب دخول في الإصدار الأول (`D-039`).

## 6. طريقة اعتماد سريعة من المالك

لا يلزم الرد على كل حقل على حدة. يمكن مراجعة الحزمة عبر اعتماد/تعديل/تأجيل هذه القرارات المجمعة:

1. **المبدأ العام:** اعتماد هذا المخطط كخط أساس للمراجعة، مع بقاء كل العناصر الموسومة غير معتمدة مفتوحة.
2. **إعادة البيع:** لا يوجد طلب بائع مستقل؛ بياناته داخل الصفقة فقط — قبول/تعديل.
3. **عدد الصفقات:** صفقة واحدة كحد أقصى لكل طلب — معتمد (`D-036`).
4. **مصدر الوصول:** قائمة قابلة للإدارة مع خيار «أخرى» وملاحظة اختيارية — معتمد (`D-038`)، والقيم الابتدائية لا تزال مفتوحة.
5. **العمولة:** تسجيل الاتفاق فقط دون تتبع السداد — معتمد (`D-037`)، وحقول الاتفاق `Q-006`.
6. **المندوب الميداني:** بيانات فقط دون حساب دخول — معتمد (`D-039`).
7. **المناطق:** مراجعة قائمة `PRD.md §2.1` وتعديلها قبل الاعتماد النهائي. «الجيزة» كمنطقة تشغيلية عامة معتمدة في `D-041`، ولا تُعاد معاملتها كسؤال مفتوح؛ تبقى بقية القائمة غير معتمدة.
8. **المدير:** صلاحيات كاملة داخل الأقسام المصرح بها مع بقاء العزل والضوابط الخاصة — معتمد (`D-040`).

## 7. ما بعد المراجعة

بعد رد المالك، تُنقل القرارات الموافق عليها فقط إلى `DECISIONS.md` وتُحدّث الوثائق المرتبطة في PR واحد متكامل. ثم تُراجع معايير القبول وتعارضات الوثائق، ويُحدد إن كان نموذج البيانات جاهزًا للتنفيذ. هذا المستند لا ينفذ تطبيقًا أو migrations ولا يدعي نجاح اختبارات.
