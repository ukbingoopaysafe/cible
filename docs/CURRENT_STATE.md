# Cible Real Estate CRM — الحالة الحالية

**آخر تحديث:** 2026-10-22
**المرحلة:** تخطيط وتوثيق — لا تنفيذ.

## 1. ما يوجد في المستودع

- `docs/planning-docs/`: خمسة مستندات مصدرية تاريخية.
- `assets/`: أصول العلامة التجارية فقط.
- `docs/`: حزمة الوثائق المرجعية الموحدة المنشأة في هذه المراجعة.
- لا يوجد `composer.json` أو تطبيق Laravel.
- لا يوجد `artisan` أو `app/` أو `routes/` أو `database/` أو migrations.
- لا توجد قاعدة بيانات أو اختبارات آلية.
- لا توجد تغييرات في كود التطبيق أو الاعتماديات أو سلوك التشغيل.

## 2. ما تمت مراجعته

تمت قراءة المستندات الخمسة كاملة، وفحص:

- حالة Git.
- هيكل المستودع.
- الأصول الموجودة.
- تعليمات المشروع المتاحة.
- التعارضات بين الخطة الأولى والقرارات اللاحقة.
- المتطلبات المذكورة في المصدر دون اعتماد صريح.
- الأسئلة التي تمنع تثبيت نموذج البيانات أو الصلاحيات أو الواجهة.

## 4. ما تم تنفيذه واختباره

**لا شيء على مستوى المنتج.**

- لم يُنفذ أي سلوك تطبيقي.
- لم تُنشأ migrations أو جداول.
- لم تُثبت أي حزمة أو اعتمادية.
- لم تُشغل اختبارات تطبيق.
- لا يوجد سلوك يمكن وصفه بـ `I — منفذ ومختبر`.

المراجعة الحالية وثائقية فقط، ولا تُعد دليلًا على أن أي متطلب وظيفي يعمل.

## 5. القرارات المثبتة

القرارات التفصيلية في [`DECISIONS.md`](./DECISIONS.md). أهمها:

- Cible CRM فقط، وليس Listing أو إدارة عقارات.
- لكل قسم سجل عميل مستقل، ويجوز أن يوجد سجل منفصل لنفس الشخص في الإيجار وإعادة البيع (`D-020`).
- فصل تشغيلي كامل بين الإيجار وإعادة البيع في سجلات العملاء والطلبات والمراحل والمتابعات والصفقات والتقارير وaftercare.
- عزل الأقسام في الـ backend وطبقة البيانات، مع قراءة المدير للقسمين فقط إلى أن يحسم `Q-018` صلاحيات الكتابة.
- لا يوجد ملف عميل مشترك، ولا بحث أو مطابقة أو ربط أو مزامنة أو دمج تلقائي بين سجلات القسمين؛ ولا يصل موظف قسم إلى سجلات القسم الآخر (`D-020`).
- `D-020` يستبدل `D-003` و`D-019`، ويعدل الجزء الخاص ببيانات العميل المشتركة في `D-005`؛ تبقى القرارات السابقة في السجل التاريخي بحالة `SUP`.
- فصل مسؤول الطلب عن مصدر الوصول.
- إلزام تاريخ متابعة قادمة لكل طلب نشط.
- عدم فرض قائمة أسباب خسارة مغلقة.
- استمرار علاقة ما بعد الصفقة بشكل مستقل داخل القسم وبالنسبة لسجل عميله، دون علاقة aftercare مشتركة بين القسمين.
- Laravel + MySQL + Filament، عربي RTL، متجاوب.
- بيانات وحدة سياقية فقط، وعمولات متغيرة بلا نسبة ثابتة.
- استيراد وتصدير Excel، وزر فتح محادثة WhatsApp مع تسجيل التواصل، ضمن الإصدار الأول (`D-021`، `D-022`). `D-014` تاريخي `SUP`.
- نطاق Excel للإصدار الأول معتمد بـ`D-023` (اعتماد المالك لـ`P-009` بتاريخ 2026-10-22). `P-009` تاريخي `SUP`. لم يبدأ تنفيذ Excel.
- تكامل WhatsApp Business API والإرسال الآلي ومزامنة المحادثات خارج النطاق.
- تفاصيل الاستيراد الأساسية معتمدة في `D-024` (`.xlsx`، استيراد جزئي، تحقق وتقرير أخطاء وإعادة محاولة). حقول القالب تبقى `Q-024` بعد `Q-001`/`Q-004`؛ حدود الملف الرقمية والتفاصيل المتبقية `Q-025`. WhatsApp يبقى `Q-026`–`Q-027`.

لا يُثبت schema أو واجهة نهائية قبل إغلاق ما يلزم منها.

## 7. التحقق المنفذ

- فحص تعريفات `DECISIONS.md` باستخدام `rg -c`: 87 معرفًا فريدًا حسب الفئات (24 `D`، و12 `S`، و10 `P`، و27 `Q`، و14 `C`)؛ آخر قرار `D-024` وآخر سؤال `Q-027`.

- لم تُشغّل اختبارات تطبيق أو أدوات بناء/تحليل كود ضمن هذا التصحيح. يظل المشروع في مرحلة التخطيط والتوثيق؛ لا يثبت هذا الفحص تنفيذ أي سلوك تطبيقي.

## 8. الخطوة التالية

**الخطوة التالية المعتمدة في السجل:** لا يوجد قرار مالك ببدء تنفيذ برمجي. نطاق Excel معتمد (`D-023`) وتفاصيل الاستيراد الأساسية (`D-024`). لم يبدأ تنفيذ Excel. تبقى حدود الملف الرقمية وتفاصيل أخرى في `Q-025`، وحقول القالب تنتظر `Q-001` و`Q-004` و`Q-024`.

**الخطوة الموصى بها:**

1. حسم `Q-001` و`Q-004` ثم اشتقاق حقول القالب في `Q-024`؛ بعدها تُعد توصية تقنية مبررة لحدود الملف الرقمية والتفاصيل المتبقية في `Q-025`.
2. الإبقاء على `Q-001` و`Q-004` و`Q-024` مفتوحة حتى تُشتق حقول القالب.
3. عدم اعتماد `P-008`؛ فهو طريقة تنفيذ غير معتمدة، ولا يبدأ تنفيذ الاستيراد قبل اعتماد الحقول والتفاصيل اللازمة.
4. عند الاعتماد فقط، بدء مرحلة تأسيس Laravel دون كتابة شاشات أو استيراد قبل اعتماد نموذج البيانات والصلاحيات.

لا يُعتبر المشروع جاهزًا للتنفيذ لمجرد اكتمال ملفات Markdown.
